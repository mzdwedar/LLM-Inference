# vLLM Inference Optimization — Llama-3.1-8B on a 24GB L4

Benchmark of three vLLM configurations serving `meta-llama/Meta-Llama-3.1-8B-Instruct` against a
long-context RAG workload on a single **NVIDIA L4 (24GB, Ada)** Vast.ai instance.

The headline: at an offered load of 8 requests/sec the **baseline sustained only 1.27 RPS**, saturated
with ~100 requests permanently queued. Chunked prefill + prefix caching, then FP8 weight quantization,
brought it to **7.25 RPS with zero queueing and zero preemptions** — median TTFT from 83.5s to 544ms.

## Hypothesis

RAG serving has a lopsided shape: prompts are long because retrieved documents are stapled to every
query, while answers are short. This workload is **~1,302 input tokens against ~96 output tokens, a
13.6:1 ratio**. Three predictions follow.

### H1 — Long prompts make TTFT the dominant latency

A request's time-to-first-token is queue wait plus prefill, and **prefill cost scales with prompt
length** while decode cost scales with output length. At 13.6:1 the input side dominates both the
user-visible wait and the GPU's work. Generating those 96 tokens is cheap; ingesting 1,302 is not.

There is a second-order effect under load. With `--no-enable-chunked-prefill`, a long prefill occupies
the scheduler step it runs in, stalling the decode of every other in-flight request — head-of-line
blocking. One long prompt degrades everyone's inter-token latency, not just its own.

### H2 — RAG prompts are highly redundant, so most of that prefill is repeated work

Retrieval returns the same documents for related queries, so requests hitting the same corpus differ
only in the question at the very end. This workload models that explicitly: requests arrive in
**bursts of 3–6 sharing one retrieval block**, so that within a burst

> **p50 6,414 of 6,546 prompt characters are byte-identical** — roughly **1,275 of ~1,302 tokens,
> ~98% of the prompt**. Only ~84 characters (**~17 tokens**), the trailing `User Query:` line, are
> unique per request.

Recomputing that shared body for every request is pure waste. vLLM's automatic prefix caching (APC)
hashes the prompt in **16-token blocks** and reuses already-computed KV for matching *leading* blocks,
so the shared body is prefilled **once per burst instead of once per request**. Because a miss breaks
the hash chain, only head-aligned reuse counts — which is exactly why the workload keeps the variable
part at the end.

Prediction: cache hit rate climbs, TTFT falls sharply, prefill throughput rises, and the GPU's work
shifts from redundant prefill toward actual decode.

### H3 — The benefit is capped by KV cache capacity

Cached blocks only help if they **survive** until the next request in the burst arrives. Prefix caching
and quantization are therefore not independent wins — on a 24GB card, bf16 weights leave so little room
for KV cache that blocks get evicted and requests preempted before the reuse can pay off. Quantizing
weights is what frees the memory that makes the cache effective. See
[Why it worked](#why-it-worked-the-24gb-memory-budget).

### Predictions vs. measured

| | Prediction | Measured |
|---|---|---|
| **H1** | Long input + short output ⇒ TTFT dominates latency | TTFT is **85%** of end-to-end latency at baseline, falling to **4%** once fixed |
| **H2** | Shared prefixes ⇒ high hit rate, prefill cost collapses | Hit rate **0% → 93%**; prefill **1,639 → 9,734 tok/s** |
| **H3** | Gains capped by KV capacity ⇒ caching alone is not enough | bf16 + APC: **60.5%** hit rate, **698** preemptions. + FP8: **93%**, **0** |

TTFT share of end-to-end latency across the three configurations: **85% → 48% → 4%**. At baseline
almost all of the user's wait happens before the first token appears; with FP8 almost none of it does.
(TTFT includes queue wait, so this tracks queueing as well as prefill — see [Caveats](#caveats).)

What would have falsified this: if TTFT were decode-bound rather than prefill-bound, or if the prompts
shared little prefix, APC would have shown a low hit rate and TTFT would not have moved. The
0% → 93% hit-rate progression tracking the TTFT collapse is the evidence for the mechanism.

## Results

Poisson rate 8.0, 2000 requests, `max_concurrency` 128. No errors in any of the three runs.

| Metric | Baseline (bf16) | + Chunked prefill & APC | + FP8 weights |
|---|---:|---:|---:|
| **TTFT** p50 | 83,498 ms | 11,518 ms | **544 ms** |
| **TTFT** p95 | 89,395 ms | 15,434 ms | **784 ms** |
| **ITL** p50 | 145.0 ms | 128.1 ms | 144.0 ms |
| **TPOT** p50 | 746 ms | 208 ms | **147 ms** |
| E2E latency p50 | 98.0 s | 24.1 s | **14.0 s** |
| Achieved RPS (of 8.0 offered) | 1.27 | 4.72 | **7.25** |
| Output tokens/sec | 145 | 538 | **839** |
| Prefill tokens/sec | 1,639 | 6,338 | **9,734** |
| Wall clock, 2000 requests | 1,573 s | 425 s | **277 s** |

Server-side counters scraped from `/metrics` during the same runs:

| Metric | Baseline | + Prefill/APC | + FP8 |
|---|---:|---:|---:|
| Prefix cache hit rate | 0.0% (disabled) | 60.5% | **93.0%** |
| KV cache usage (mean) | 95.5% | 91.6% | **48.9%** |
| Requests waiting (mean) | 100.3 | 47.1 | **0.0** |
| Requests running (mean / max) | 21.4 / 23 | 68.5 / 128 | **110.6 / 128** |
| Preemptions (total) | 125 | 698 | **0** |

The second table is where the mechanism shows up. The baseline never had more than **23 requests
resident** while ~100 waited; the FP8 run held the full 128-request cap with its KV cache still
half empty and never preempted once.

Note the preemption count *rises* in config 2 (125 → 698). Prefix caching and chunked prefill let
vLLM admit far more requests concurrently (21 → 69 resident), but the bf16 weights still leave too
little KV cache to hold them, so the scheduler thrashes. Config 2 is faster overall despite this;
it is config 3 that removes the pressure rather than just redistributing it.

## Why it worked: the 24GB memory budget

Approximate budget on the L4, and it lines up with what the server actually did:

- `--gpu-memory-utilization 0.90` of 24GB ≈ **21.6 GB** total budget
- bf16 weights ≈ **16.1 GB** → roughly **4 GB** left for KV cache after activations and CUDA graphs
- KV per token = 32 layers × 8 KV heads × 128 dim × 2 (K,V) × 2 bytes = **128 KiB/token**
- 4 GB ÷ 128 KiB ≈ 30k tokens ÷ ~1,302-token prompts ≈ **~23 concurrent requests**

That derivation predicts ~23, and the measured baseline `num_requests_running` peaked at exactly
**23**. The baseline wasn't slow at generating tokens — it could only admit about a sixth of the
offered concurrency, and everything else sat in the queue. Its 83.5s TTFT is mostly queue wait.

FP8 halves weight memory to ≈ **8.0 GB**, leaving ~12 GB for KV — roughly 3× the blocks. Combined
with 93% prefix-cache reuse (the shared RAG prefixes are stored once instead of per request), the
server sustained all 128 in-flight requests at under half its KV capacity.

**The throughput win comes from admission, not arithmetic.** FP8 on Ada does have faster tensor
cores, but the decisive effect here is that smaller weights buy enough KV cache to stop queueing
and preempting.

## Concurrency scaling

Fixed-concurrency sweep against the FP8 server, 30s per step:

| Streams | RPS | TTFT p50 | TTFT p95 | ITL p50 | Output tok/s | Errors |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.13 | 146 ms | 217 ms | 36.3 ms | 27 | 0 |
| 2 | 0.30 | 186 ms | 212 ms | 36.8 ms | 53 | 0 |
| 4 | 0.70 | 193 ms | 258 ms | 37.9 ms | 102 | 0 |
| 8 | 1.53 | 201 ms | 283 ms | 40.2 ms | 191 | 0 |
| 16 | 2.87 | 223 ms | 390 ms | 44.2 ms | 345 | 0 |
| 32 | 4.50 | 249 ms | 349 ms | 52.9 ms | 579 | 0 |
| 64 | 6.27 | 333 ms | 517 ms | 74.9 ms | 804 | 0 |
| 128 | 7.10 | 504 ms | 947 ms | 117.8 ms | 949 | 0 |
| 256 | 9.57 | 1,241 ms | 2,922 ms | 163.4 ms | 1,246 | 29 |
| 500 | 10.63 | 1,748 ms | 14,206 ms | 176.7 ms | 1,188 | 81 |

Reading the curve:

- **TTFT stays flat to ~32 streams** (146 → 249 ms) — continuous batching absorbing load with
  almost no queueing cost.
- **The knee is at 128 streams**: TTFT p95 still sub-second (947 ms) at ~950 output tok/s, the
  best throughput with latency intact.
- **256 streams is past capacity**: first errors appear (29), p95 triples to 2.9s. At 500 streams
  p95 reaches 14.2s for barely more throughput — the queue is growing faster than it drains.

For a 1s TTFT p95 SLA, **128 concurrent streams** is the operating point.

## Caveats

- **The baseline was saturated, not merely slow.** It sustained 1.27 of 8.0 offered RPS, so its
  TTFT figures are dominated by queue wait, not per-request speed. The comparison shows the
  baseline could not serve this load at all; it is not a clean per-request speedup measurement.
- **ITL barely moves across configs** (145 / 128 / 144 ms), which is expected — ITL measures
  decode-only gaps, and decode is memory-bandwidth-bound on the L4. But the three runs had very
  different resident batch sizes (21 / 69 / 111), so cross-config ITL is not apples-to-apples. The
  clean single-stream number is **36.3 ms** from the sweep at concurrency 1.
- **TPOT ≫ ITL for the baseline** because TPOT is end-to-end latency ÷ output tokens and therefore
  amortizes TTFT, while ITL is the inter-token gap. Where TTFT is small they converge: for the FP8
  run, (14.0s − 0.544s) / 96 ≈ 140 ms ≈ its 144 ms ITL.
- **"Incomplete" request counts in the sweep are an artifact** of the 30s cutoff truncating
  in-flight requests, not failures. Only the 256- and 500-stream steps have genuine errors.
- **Only weights and activations are quantized** (FP8 W8A8 dynamic); the **KV cache remains bf16**.
- Configuration changes are cumulative, so each column is not an independent ablation.
- Single run per configuration, no repeats, so run-to-run variance is unmeasured.

## Reproducing

```bash
python scripts/generate_prompts.py              # regenerate data/rag_workload.jsonl
python scripts/scrape_metrics.py <config>       # server-side /metrics, through the SSH tunnel
jupyter lab notebooks/analysis.ipynb            # parse the raw reports (local only, see below)
```

Raw reports are in `results/exp2/` (`vllm-rag-*.json` = guidellm client metrics,
`vllm_metrics_*.json` = server-side scrapes). `results/exp1/` is an earlier run kept for reference;
every number on this page comes from `exp2`.

Credentials (HF token, NGC key, GPU host and port) come from a gitignored `.env` — copy
`.env.example` to `.env` and fill it in, then `set -a; source .env; set +a`.
